1. Visão Geral da Arquitetura e Entidade Aviao

O sistema integra um backend REST desenvolvido em Java 25 + Spring Boot 4.1.1 + Spring Data JPA com um frontend web construído em HTML5, CSS3 e JavaScript puro (Fetch API), servido diretamente pelo Spring Boot através da pasta src/main/resources/static/.

3. Respostas às Perguntas da Apresentação Individual

1. Como o frontend realiza uma requisição HTTP ao backend?

O frontend realiza as requisições utilizando a Fetch API nativa do navegador (fetch(url, options)) dentro de funções JavaScript assíncronas (async / await) no arquivo script.js.

A URL base do backend é definida em const API_URL = "http://localhost:8081/aviao";. Quando o usuário interage com um botão da interface (por exemplo, Cadastrar Aeronave ou Buscar por Nome), o evento dispara a função correspondente, que monta as configurações da requisição (verbo HTTP, cabeçalhos e corpo quando necessário) e executa await fetch(...) contra o servidor Spring Boot na porta 8081, tratando erros de rede e de status HTTP com try / catch.

2. Como são utilizados os verbos HTTP (GET, POST, PUT, DELETE) implementados no projeto?
  • POST POST /aviao (Criar): Enviado por salvarAviao() com os dados do novo avião em JSON para salvar um registro inédito no PostgreSQL.
  • GET GET /aviao?nome={nome} e GET /aviao/todos (Consultar): Enviado por buscarAviaoPorNome() para buscar uma aeronave específica e por carregarFrota() para listar toda a frota cadastrada.
  • PUT PUT /aviao?id={id} (Atualizar): Enviado por atualizarAviaoPorId() informando o id na URL e os campos atualizados em JSON no corpo da requisição.
  • DELETE DELETE /aviao?nome={nome} (Remover): Enviado por deletarAviaoPorNome(), após confirmação do usuário, passando o nome exato da aeronave na URL para remoção no banco.
3. Como os dados são enviados do frontend para o backend?

Os dados são enviados de duas maneiras, conforme o contrato definido em AviaoController.java:

  1. Corpo da Requisição em JSON (@RequestBody — POST e PUT): O JavaScript reúne os valores do formulário em um objeto, converte em string JSON com JSON.stringify(dadosAviao) e envia o cabeçalho "Content-Type": "application/json" para que o Spring/Jackson desserialize o JSON para a classe Aviao.
  2. Parâmetros na URL / Query String (@RequestParam — GET, DELETE e id do PUT): Os valores são concatenados após ? usando encodeURIComponent() (ex.: http://localhost:8081/aviao?nome=E195-E2 ou http://localhost:8081/aviao?id=1), sendo capturados pelo Spring via @RequestParam.
4. Como o backend processa a requisição e retorna uma resposta?
  1. Recepção (AviaoController): O Spring Web mapeia a rota /aviao e o verbo HTTP, valida a origem via @CrossOrigin(origins = "*") e extrai o @RequestBody / @RequestParam.
  2. Lógica de Negócio (AviaoService): O controller delega ao serviço. No PUT, o serviço busca o registro por ID e mescla campos novos e antigos via Aviao.builder(); no GET por nome, busca no repositório e lança exceção caso não encontre.
  3. Persistência (AviaoRepository + PostgreSQL): O Spring Data JPA executa o SQL correspondente (INSERT, SELECT, UPDATE ou DELETE) no banco cadastro_aviao.
  4. Retorno HTTP (ResponseEntity): POST, PUT e DELETE devolvem ResponseEntity.ok().build() (status 200 OK sem corpo). Os métodos GET devolvem ResponseEntity.ok(...) contendo o objeto Aviao ou List<Aviao> serializado em JSON pelo Jackson.
5. Como o frontend recebe e apresenta os dados retornados pelo backend?

Após receber o objeto response do fetch, o script.js verifica if (!response.ok). Se houver erro HTTP, exibe uma mensagem clara no banner superior e registra o detalhe no Monitor HTTP.

Em caso de sucesso: nos métodos GET, chama await response.json() para transformar o JSON em objetos JavaScript; nos métodos POST, PUT e DELETE, confirma o status 200 OK e dispara await carregarFrota(false) para recarregar a tabela. Todos os valores exibidos na ficha técnica (exibirResultadoBusca) e na tabela (renderizarTabelaFrota) são inseridos com segurança usando document.createElement() e .textContent.

6. Como o prompt elaborado orientou a IA na geração da interface?

O prompt forneceu uma especificação técnica fechada baseada no código real do backend: listou os atributos exatos da classe Aviao, a URL e a porta (8081), o formato esperado de cada endpoint (@RequestBody vs @RequestParam), a inclusão controlada de @CrossOrigin(origins = "*") e GET /aviao/todos, o layout em 4 blocos com temática de aviação (incluindo o Monitor HTTP para demonstração em sala) e regras rígidas de segurança no JavaScript (validação de inputs, encodeURIComponent e prevenção de XSS sem innerHTML).

4. Prompt Refinado Utilizado (Pronto para Entrega)

Tenho um backend REST em Java (Spring Boot) rodando na porta 8081 com banco PostgreSQL, cuja entidade Aviao (tabela "aviao") possui exatamente os seguintes campos JSON:
- id (Integer, gerado automaticamente pelo banco)
- nome (String)
- modelo (String)
- fabricante (String)
- autonomia (Integer, em km)
- capacidade (Integer, número de passageiros)

Atualmente o AviaoController (@RequestMapping("/aviao")) possui estes endpoints:
1. POST /aviao -> recebe @RequestBody Aviao (JSON) e retorna 200 OK sem corpo (Void).
2. GET /aviao?nome={nome} -> recebe @RequestParam String nome e retorna 200 OK com o objeto Aviao em JSON.
3. PUT /aviao?id={id} -> recebe @RequestParam Integer id na URL e @RequestBody Aviao (JSON) no corpo, retornando 200 OK sem corpo (Void).
4. DELETE /aviao?nome={nome} -> recebe @RequestParam String nome na URL e retorna 200 OK sem corpo (Void).

2. Criação do Frontend na pasta src/main/resources/static/ (index.html, style.css e script.js):

   - Previna vulnerabilidades XSS renderizando todos os dados recebidos do backend via document.createElement() e textContent (nunca injete dados externos com innerHTML).
   - Trate erros HTTP verificando response.ok e capture falhas de rede com try/catch, exibindo feedback claro ao usuário.
   - Atualize automaticamente a tabela da frota após operações de POST, PUT e DELETE bem-sucedidas.
